# Plex Burner: notes for contributors and AI assistants

Self-hosted app that copies DVDs and home video discs into a Plex, Jellyfin or Emby library from a web dashboard.

- Backend: Python (Flask served by waitress) in `app/`. `app/main.py` wires the modules together and holds the API
  routes; its docstring lists what each module does. Settings, saved locations and copy history live in one JSON file
  in the data folder (`app/appsettings.py`). Preview frames are cached in `data/thumbs`.
- Disc work uses command line tools installed in the Docker image: `ffmpeg` (DVD reading via its `dvdvideo` demuxer,
  remuxing, converting, frames), `lsdvd` (disc details), `dvdbackup` (fallback and full disc backups), `7z` (data discs),
  `eject`. `libdvd-pkg` builds libdvdcss for encrypted discs.
- One `DiscWorker` (`app/disc.py`) per drive, created by `app/drives.py`, which rescans `/sys/block/sr*` every few seconds.
- Frontend: no build step. `app/static/index.html` (markup), `app/static/app.css`, and one script per tab in
  `app/static/js/` (`core.js` loads first with helpers, dialogs and the `Tabs` registry; `boot.js` last).
- `app/static/demo.js` is a simulated API for the public demo. Any new endpoint the UI calls needs a demo response,
  and any new image URL needs a case in `image()`.
- GitHub Pages site in `docs/`: landing page (`docs/index.html`, which shows `CHANGELOG.md`) plus `docs/demo/`,
  generated by `scripts/build-pages.sh`. Screenshots in `docs/img/` are taken from the demo.

## Release rules (do this for EVERY change pushed to main)

Installed copies update themselves from `main` using `app/VERSION`, so:

1. **Bump `app/VERSION`** using semver: patch for fixes, minor for new features, major for breaking config changes.
2. **Add a `CHANGELOG.md` entry** at the top: `## [x.y.z] - YYYY-MM-DD` with `### Added`, `### Changed`, `### Fixed`
   or `### Removed` subsections. Write entries for users, not developers. The website renders this file.
3. If the frontend or `demo.js` changed, run `./scripts/build-pages.sh` so `docs/demo/` matches the app (CI checks).
   Re-take the screenshots in `docs/img/` if the UI looks different.
4. Prefer in-app settings (`app/appsettings.py`, Settings tab) over environment variables. If you do add an
   environment variable, document it in `README.md`, the config table in `docs/index.html` and `.env.example`.
5. Never require edits to tracked files for configuration. User settings live in `.env` and `data/`, so
   `git merge --ff-only` updates never conflict.
6. Keep `main` deployable: updates are a fast-forward of `main`, then `pip install -r requirements.txt` when it
   changed, then a restart. Changes to the `Dockerfile` (new system packages) need `docker compose up -d --build`,
   so say so in the changelog.
7. Never restart or update while a disc is copying. `updater.busy` guards this.

## Style
- No em dashes in any user-facing text or docs.
- Dark theme with amber accent (`#f5a524`), violet secondary (`#a78bfa`), monospace for numbers and paths.
- Frontend has no build step and no external CDN dependencies (it must work on an offline LAN).
- Never put personal details (real usernames, hostnames, IPs, paths) in `demo.js`, screenshots or the website.
  Use public-domain film titles in examples.

## Test locally
```bash
pip install -r requirements.txt
DATA_DIR=./data MEDIA_PATHS=/tmp/media PORT=9000 python -m app.main     # real data (needs a drive for discs)
# open http://localhost:9000/?demo for simulated data
```
